# 「途变」全域行程自适应 Agent —— 开发步骤文档

> 本文档是「途变」项目的**落地实施路线图**：把《需求文档》《开发文档》的设计，拆解成可逐条执行的开发步骤。
> 每步包含：**目标 → 产出文件 → 关键实现要点 → 验收标准**。
> 开发按本文档顺序执行，代码已同步落地到 `server/`（后端 Agent）与 `app/`（HarmonyOS 客户端）。

## 1. 第 1 步：搭建后端工程

**目标**：建立可运行的 FastAPI 工程骨架。

**产出**：`server/requirements.txt`、`server/app/main.py`、各 `__init__.py`

**要点**：
- 依赖仅 `fastapi`、`uvicorn`、`pydantic`、`pytest`、`httpx`。
- `main.py` 创建 `FastAPI()` 实例，挂载 CORS（供真机/预览器跨域联调）。

**验收**：`uvicorn app.main:app --reload` 可启动；`GET /api/health` 返回 `{"success":true}`。

---

## 2. 第 2 步：数据模型（schemas.py）

**目标**：用 Pydantic 定义前后端契约，与《开发文档》§6 一致。

**产出**：`server/app/models/schemas.py`

**要点**：定义以下模型与枚举：

| 模型 | 关键字段 |
|---|---|
| `TravelGoal` | origin, destination, departure_time?, deadline, budget?, luggage, preference, companions |
| `TravelPreference` | 准时优先 / 省钱优先 / 少步行 / 少换乘 / 舒适优先 |
| `RouteSegment` | mode, from, to, start_time?, end_time?, duration_minutes, distance_meters?, cost?, note? |
| `RoutePlan` | plan_id, type(主方案/Plan B/重规划方案), eta, cost, duration_minutes, walk_distance_meters, transfer_count, risk_level(低/中/高), on_time_probability, segments, reason |
| `JourneyState` | 出发准备/去车站/候车/乘车/到站换乘/前往目的地/入场或入住准备/已抵达 |
| `ReplanResult` | trigger, old_plan_status, new_plan, extra_cost, action, explanation, risk_level |
| `LocationData` | lat, lng, accuracy, timestamp |
| `WeatherData` | city, weather, temperature, warning |
| `JourneyContext` | now, location?, weather?, depart_late_minutes |

**验收**：`TravelGoal(...)`、`RoutePlan(...)` 可正常实例化与 `model_dump()`。

## 3. 第 3 步：目标解析（goal_parser.py）

**目标**：把自然语言转成 `TravelGoal`，缺失字段走表单兜底。

**产出**：`server/app/core/goal_parser.py`

**要点**：
- 规则 + 正则/关键词提取：出发地（`从…`/`在…`）、目的地（`去…`/`到…`）、截止时间（`X点/XX:XX 前`/`必须`）、预算（`预算N元`）、行李（`行李箱/行李/背包`）、偏好（`准时/省钱/少步行/少换乘/舒适`）。
- 缺失关键字段（origin/destination/deadline）返回 `missing_fields`，由客户端引导补充（表单）。
- 预留 `parse_with_llm(text)` 接口，后续接入大模型结构化输出（需求文档 §8.4、§11.1）。

**验收**：输入「我明天从杭州东站去上海看演唱会，带一个行李箱，预算300元，晚上7点前必须入场」→ 解析出 origin=杭州东站、destination=上海演唱会场馆、deadline=19:00、budget=300、luggage=true、preference=准时优先。

## 4. 第 4 步：路线生成与评分（route_planner.py / route_scorer.py）

**目标**：生成候选路线，并按规则引擎评分排序。

**产出**：`server/app/core/route_planner.py`、`route_scorer.py`

**要点**：
- `route_planner`：从 `map_service` 取候选路线（高铁+地铁+步行 / 高铁+网约车 / 全程网约车 / 地铁为主 等），组装 `RoutePlan.segments` 与汇总字段。
- `route_scorer`：实现《开发文档》§9.3 伪代码，评分维度：

| 维度 | 规则 |
|---|---|
| 超时 | `eta > deadline` 扣 50 |
| 超预算 | `cost > budget` 扣 20 |
| 带行李长步行 | `luggage && walk > 800m` 扣 15 |
| 恶劣天气长步行 | 暴雨/大雨且 `walk > 500m` 扣 20 |
| 换乘过多 | `transfer >= 3` 扣 10 |
| 准时偏好 | `preference==准时优先` 加分 `on_time_probability * 20` |
| 少步行偏好 | `walk` 越长扣分越多 |
| 夜间安全 | 22:00 后行程加安全权重 |

- `score` 归一化到 `on_time_probability`（0~1），供前端展示准时风险。

**验收**：对同一目标，评分能正确区分「准时但贵」与「便宜但可能迟到」的路线；主方案为评分最高者。

---

## 5. 第 5 步：Plan B 生成（plan_b.py）

**目标**：主方案之外，针对已知风险预置备选方案。

**产出**：`server/app/core/plan_b.py`

**要点**：实现《开发文档》§9.4 触发规则：

| 触发条件 | 生成方案 |
|---|---|
| `eta > deadline` | 准时优先方案（压缩换乘、提高打车） |
| 暴雨/大雨 且 步行长 | 少步行方案（网约车到室内入口） |
| `luggage && walk > 800m` | 网约车接驳方案 |
| `depart_late > 10min` | 切换准时优先策略 |
| `transfer >= 3` | 少换乘方案 |

**验收**：给定「带行李箱 + 主方案步行 1200m」→ 自动生成「网约车接驳」Plan B，并附带 `trigger` 与 `reason`。

---

## 6. 第 6 步：旅程状态机（journey_state_machine.py）

**目标**：维护用户旅程阶段，输出下一步动作。

**产出**：`server/app/core/journey_state_machine.py`

**要点**：实现《开发文档》§9.5 伪代码 + 每阶段 `next_action`（提醒文案，需求文档 §7.6）：

| 阶段 | next_action 示例 |
|---|---|
| 出发准备 | 建议 XX:XX 出门，带好证件/雨具/行李 |
| 去车站 | 预计 XX:XX 到站，留意检票口 |
| 候车 | 车次 G7xxx，检票时间 XX:XX |
| 乘车 | 即将到站，注意下车出口 |
| 到站换乘 | 建议选择地铁/网约车 |
| 前往目的地 | 接近目的地，注意入口与集合点 |
| 入场或入住准备 | 完成入场/入住 |
| 已抵达 | 显示总结 |

**验收**：给定 location + plan，能正确判断处于哪个阶段并返回 `next_action`。

---

## 7. 第 7 步：重规划（replanner.py + explanation.py）

**目标**：判断原计划是否失效，失效则给出新方案与原因。

**产出**：`server/app/core/replanner.py`、`explanation.py`

**要点**：实现《开发文档》§9.6 `should_replan` 判断依据（需求文档 §7.7）：

- ETA 超时、恶劣天气长步行、带行李长步行、出门晚、路线耗时变化、超预算。

`explanation.py`：把技术结果转成用户可读文本，遵守文案规范（短、明确、可执行）：

> 原计划预计 19:12 到达，已超过 19:00 入场要求。建议切换为网约车方案，预计 18:48 到达，费用增加约 42 元。

**验收**：模拟「暴雨 + 步行 850m」→ `should_replan=True`，产出 `ReplanResult`（trigger/old_plan_status/new_plan/extra_cost/action/explanation）。

## 8. 第 8 步：Mock 数据服务（services/）

**目标**：天气/地图/定位三类外部数据的可替换实现。

**产出**：`services/weather_service.py`、`map_service.py`、`location_service.py`

**要点**：
- 每个 service 定义 `async def get_xxx(...)` 接口，内部先返回 Mock 数据；**预留真实 API 密钥注入点**（需求文档 §7.3、§10）。
- `map_service` 内置「杭州东站 → 上海演唱会场馆」演示用候选路线（复用 SmartTravel `resources/rawfile/data` 的思路，本工程内联）。
- 异常兜底：API 失败时返回缓存/默认值（需求文档 §13）。

**验收**：三个 service 可独立调用并返回结构正确的数据。

## 9. 第 9 步：REST API（api/routes.py）

**目标**：暴露前端需要的 4 个接口 + 通用响应格式。

**产出**：`server/app/api/routes.py`

**要点**：统一响应 `{success, data, message}`（《开发文档》§8.1）：

| 接口 | 方法 | 输入 | 输出 |
|---|---|---|---|
| `/api/health` | GET | - | 服务状态 |
| `/api/parse-goal` | POST | `{text}` | TravelGoal + missing_fields |
| `/api/plan-route` | POST | `{goal, location?}` | mainPlan + backupPlans + riskTips |
| `/api/update-status` | POST | `{goal, plan, location?, now}` | currentState + nextAction + needReplan + reason |
| `/api/replan` | POST | `{goal, currentPlan, context}` | ReplanResult |

**验收**：`httpx` 依次调用 4 接口能跑通完整主链路。

## 13. 第 13 步：HarmonyOS 客户端 —— 组件与页面

## 14. 第 14 步：联调与验收

**目标**：端到端跑通演示脚本（需求文档 §15.3）。

**验收脚本**：

```text
1. 打开途变 App
2. 输入：我明天从杭州东站去上海看演唱会，带一个行李箱，预算300元，晚上7点前必须入场
3. 系统识别目标并补充偏好
4. 展示高铁 + 地铁 + 步行主方案
5. 展示高铁晚点后的网约车 Plan B
6. 触发暴雨事件
7. 系统判断步行风险升高
8. 推荐改为网约车到室内入口
9. 展示额外费用和预计到达时间
10. 显示最终准时到达总结
```

**MVP 完成标准**（《开发文档》§15）：
- 可输入目标、生成主方案与 Plan B、展示时间轴/卡片/风险；
- 可模拟或真实触发暴雨/出门晚/ETA 超时 → 进入重规划页；
- 展示新方案与原因、到达总结；
- 接入定位、天气、地图中至少两项（本版为 Mock 实现，接口已预留真实数据接入点）。
